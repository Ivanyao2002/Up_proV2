## FLT-UPLOAD-01 — Images / documents non envoyés à la création

### Problème

Lors de la création d’un **chauffeur** ou d’un **véhicule** depuis le back-office ou le portail partenaire, l’utilisateur peut sélectionner des fichiers (KYC chauffeur, carte grise, assurance, etc.) mais **ces images ne sont pas transmises à l’API** en mode v1.

### Constat front (9 juin 2026)

| Flux | Comportement actuel |
|------|---------------------|
| Création véhicule + chauffeur (`applyVehicleCreateFlow`) | Upload pièces véhicule : `try/catch` silencieux — **aucun appel v1** |
| Création chauffeur (`createDriverWithDocumentsViaV1`) | Compte créé via `POST /v1/auth/driver/register` + onboarding, mais **fichiers KYC ignorés** (commentaire : « routes v1 dédiées à brancher ») |
| Mode legacy | Seul le **nom de fichier** est envoyé (`filename`), pas le binaire |

### Impact

- Chauffeurs / véhicules créés **sans aucun document** malgré la sélection de fichiers dans le formulaire.
- Renforce l’incohérence **FLT-COMPLIANCE-01** (`kyc_status=approved` avec `kycDocuments=[]`).

### Demande backend

1. **Upload fichier** : confirmer ou exposer `POST /v1/files` (multipart) → `fileId`.
2. **Documents chauffeur** : `POST /v1/drivers/{driverId}/documents` (multipart ou `{ type, fileId }`).
3. **Documents véhicule** : `POST /v1/partners/{partnerId}/vehicles/{vehicleId}/documents` (ou équivalent admin).
4. Documenter les **types attendus** (`ID_CARD`, `DRIVER_LICENSE`, `PROFILE_PHOTO`, `REGISTRATION`, `INSURANCE`, etc.) alignés avec le front (`VehicleCreatePiecesSection`, `VehicleCreateDriverDocumentsSection`).

### Front (en attente API)

Une fois les routes disponibles, brancher `vehicleCreateFlow.ts` et `partnerDrivers.v1.service.ts` pour envoyer les fichiers réels après création du compte / véhicule.

## FLT-PAIR-01 — Création couplée chauffeur + véhicule

### Règle métier

On ne doit **pas** pouvoir créer un chauffeur sans véhicule ni un véhicule sans chauffeur.

### Front (livré 9 juin 2026)

| Écran | Comportement |
|-------|--------------|
| Admin `/admin/fleet/vehicles/new` | Chauffeur **obligatoire** |
| Admin `/admin/network/partners/{id}/drivers/new` | Redirige vers formulaire **véhicule + chauffeur**, partenaire verrouillé |
| Portail `/partner/fleet/new` | Chauffeur **obligatoire** |
| Portail `/partner/drivers/new` | Redirection vers `/partner/fleet/new` |

### Demande backend (optionnel mais recommandé)

- Endpoint transactionnel ou validation serveur : refuser un chauffeur sans `current_vehicle_id` actif, ou un véhicule sans `driver_id` assigné (selon règles métier finales).
- Ou `POST /v1/partners/{id}/fleet-pairs` créant chauffeur + véhicule + assignation en une requête.

## FLT-COMPLIANCE-01 — Complétude documentaire chauffeurs & véhicules (liste + filtres)

### Problème

Le back-office doit identifier et traiter les chauffeurs et véhicules **sans documents** ou **dossier incomplet**. Aujourd’hui :

1. **La liste** (`GET /v1/admin/drivers`, `GET /v1/admin/vehicles`) ne porte **aucune info documentaire** (pas de compteur, pas de types manquants).
2. **`kyc_status` est incohérent** avec la réalité des documents en détail.
3. Pour savoir si un chauffeur a des documents, il faudrait **N appels détail** (ex. 1156 chauffeurs → 47 pages × 1 GET `/drivers/{id}` chacun).

### Constat live (9 juin 2026)

#### Liste — `GET /v1/admin/drivers`

Champs présents par item : `kyc_status`, `approval_status`, `current_vehicle_id`, `vehicleLabel`, `partnerName`, `zoneName`, etc.

**Absents** : `documentsCount`, `missingDocumentTypes`, `documentsSummary`, `complianceStatus`, documents véhicule.

#### Incohérence `kyc_status` vs détail

| Chauffeur | Liste `kyc_status` | Détail `kycDocuments` |
|-----------|-------------------|------------------------|
| `23dc0b82-8d9b-4b9f-9fab-c63160b809f4` | `approved` | **`[]` (0 document)** |
| `f41e92f5-5809-4ebf-9f2c-89df6bb2b33f` | `approved` | **5 documents** (`ID_CARD`, `DRIVER_LICENSE`, `PROFILE_PHOTO`, `INSURANCE`, `REGISTRATION_CARD`) |

→ Un chauffeur peut être **approuvé KYC** alors qu’**aucun document** n’est attaché. Le filtre / badge « KYC approuvé » ne permet pas de trouver les dossiers à compléter.

#### Autres signaux utiles déjà en liste (insuffisants seuls)

| Champ | Exemple | Limite |
|-------|---------|--------|
| `current_vehicle_id` | `null` | Indique pas de véhicule, pas l’état doc véhicule |
| `vehicleLabel` | `"ECO"` ou `"PREMIUM"` | Catégorie seule, pas plaque ni docs |
| `kyc_status` | `approved` / `pending` | Non fiable vs documents réels |

#### Véhicules — `GET /v1/admin/vehicles`

Exemple item :

```json
{
  "id": "4276a26a-ae3c-4649-81e3-44afc15623f3",
  "plate_number": "SMOKE-4076",
  "status": "pending",
  "driver_id": null
}
```

**Aucun champ** : `documentsSummary`, types manquants, lien docs carte grise / assurance.

### Impact front (état actuel)

| Écran | Comportement |
|-------|--------------|
| **Admin / Flotte / Chauffeurs** | Colonnes nom, zone, partenaire, statut — **pas de colonne documents** |
| **Fiche chauffeur** | Onglet KYC avec documents (**détail uniquement**) |
| **File KYC** | `GET /v1/admin/kyc/queue` — validation des docs soumis, **pas** « sans aucun document » |
| **Admin / Flotte / Véhicules** | Pas de visibilité documentaire en liste |

Le front peut compléter les slots manquants en **détail** (`mergeExpectedDriverKycSlots` : CNI, permis, selfie), mais **impossible en liste** sans données backend.

## PA-STATUS-01 — Activation / changement de statut partenaire (admin)

### Problème

Le back-office admin doit pouvoir **approuver**, **activer** ou **suspendre** un partenaire (`pending` → `active`, etc.). Aucune route fiable n’est disponible aujourd’hui.

### Constat live (9 juin 2026)

| Route testée | Résultat |
|--------------|----------|
| `PATCH /v1/partners/{id}` avec `{ "status": "active" }` | **HTTP 200** mais le `status` reste **`pending`** (champ ignoré) |
| `PATCH /v1/partners/{id}` avec `{ "status": "suspended" }` | Idem — **pas de changement** |
| `POST /v1/admin/partners/{id}/approve` | **404** — route inexistante |
| `PATCH /v1/admin/partners/{id}` | **404** — route inexistante |
| `GET /v1/admin/approval-requests` | **200** — file vide (workflow générique non alimenté pour les partenaires) |
| `POST /v1/admin/approval-requests/{id}/approve` | Documenté Swagger — **non testé** faute de demande en file |

Autres champs sur `PATCH /v1/partners/{id}` : `contactPhone` / `contact_phone` **fonctionnent** — seul le **statut** n’est pas appliqué.

### Impact front

| Écran | Comportement |
|-------|--------------|
| `PartnersListPage` / `PartnerDetailPage` | Affiche le statut (`pending`, `active`, `suspended`) — **aucun bouton** Approuver / Suspendre |
| `partners.service.ts` | Seulement `listAdmin` + `create` — **pas de `updateStatus`** |

## CORS-01 — PATCH / PUT / DELETE bloqués en navigateur

### Problème

Les mutations (`PATCH`, `PUT`, `DELETE`) vers `https://api.upjunoo-dev.tech` échouent en **CORS** depuis le front (ex. modification partenaire), alors que les `GET` et `POST` passent.

### Constat (9 juin 2026)

Préflight `OPTIONS` sur `/v1/partners/{id}` avec `Origin: http://localhost:3000` :

```
Access-Control-Allow-Methods: GET, HEAD, POST
```

→ **`PATCH` absent** — le navigateur bloque la requête avant envoi.

Même constat pour `PUT` et `DELETE`. L’API répond bien en **200** si appelée sans CORS (curl, scripts Node).

### Contournement front (livré)

- Rewrite Next.js : `/upjunoo-api/:path*` → `{NEXT_PUBLIC_API_URL}/:path*`
- `fetchClient` : en navigateur, les appels passent par `/upjunoo-api/...` (same-origin, pas de preflight cross-origin)

**Redémarrer le serveur dev** (`npm run dev`) après mise à jour de `next.config.ts`.

### Attendu backend

Ajouter **`PATCH`**, **`PUT`** et **`DELETE`** à `Access-Control-Allow-Methods` (et headers custom si besoin : `X-Client-Type`, `X-Scope`, etc.) pour les origines autorisées (`localhost:3000`, domaine prod du back-office).

## OR-TRACK-01 — Suivi dynamique de la trajectoire chauffeur (prise en charge + destination)

### Besoin métier

Le back-office doit pouvoir **tracer la trajectoire réelle du véhicule** pendant une course active, en distinguant clairement :

| Phase | Signification UI | Exemple libellé |
|-------|------------------|-----------------|
| **`to_pickup`** | Chauffeur **en route vers le client** (prise en charge) | « En route vers le client » |
| **`at_pickup`** | Chauffeur **arrivé au point de prise en charge** | « Arrivé · attente client » |
| **`to_dropoff`** | Client à bord · chauffeur **en route vers la destination** | « En route vers la destination » |
| **`completed`** | Course terminée · tracé figé (lecture seule) | « Course terminée » |

Objectif : sur la **fiche course** et la **carte live**, afficher non seulement la position actuelle, mais **le chemin parcouru** selon la phase (récupération client **ou** dépôt à destination).

### Constat front (9 juin 2026)

| Carte course `TripRoutePreview` | Segment **droite** pickup → dropoff (Mapbox ou fallback SVG) | Ce n’est **pas** la trajectoire réelle du véhicule |
| Carte live `liveMap.mapper` | `trip_routes[]` = ligne droite entre pickup et dropoff | Idem — pas de tracé dynamique par phase |
| Détail commande `GET /v1/admin/orders/{id}` | Bloc `tracking: {}` souvent **vide** | Pas exploitable pour le suivi |
| Position embarquée | `tracking.driverLocation` parfois présent via mapper `adminOrderVehicle.ts` | **Instantané** uniquement |

```json
  "polyline": "encoded_polyline_or_geojson_linestring"

```

- Limiter le volume : échantillonnage (ex. 1 point / 5 s en mouvement) + dernier point toujours inclus.

## MK-BAN-01 — Bannières marketing (image app mobile client)

### Contexte produit

Les **bannières** sont des **images** affichées sur l’**application mobile client** (carrousel / hero). Le back-office propose un formulaire « Nouvelle bannière » (`/admin/marketing/banners/new`) qui ne demande aujourd’hui **aucune image** — seulement titre, emplacement, dates et statut.

### État API (audit live — 9 juin 2026)

| Route | Méthode | Résultat |
|-------|---------|----------|
| `/v1/admin/marketing/banners` | GET | **200** — liste admin OK |
| `/v1/admin/marketing/banners` | POST | **400** — `MARKETING_BANNER_CREATE_FAILED` : `Could not find the 'code' column of 'app_banners' in the schema cache` |
| `/v1/app-banners` | GET | **200** — lecture bannières **app mobile client** (liste vide en dev) |
| `/v1/app-banners` | POST | **404** — route inexistante |
| `…/banners/upload`, `/v1/media/upload`, `/v1/uploads` | POST | **404** — **aucun endpoint d’upload fichier** trouvé |

### Constats

1. **Pas d’upload multipart** : impossible d’envoyer un fichier image directement depuis le front aujourd’hui.
2. **Création JSON bloquée** : même avec `image_url` / `imageUrl` dans le body, l’erreur DB `code` column survient avant validation image.
3. **Swagger incomplet** : seul `GET /v1/app-banners` documenté — pas de schéma POST ni champs image (`image_url`, `imageUrl`, `media_url`…).
4. **Emplacements formulaire** : options actuelles (`home_hero`, `driver_app`, `partner_portal`) ne ciblent pas explicitement l’**app client** — à aligner avec les `placement` réels de `app_banners`.

### Payload front actuel (insuffisant)

```json
{
  "title": "…",
  "placement": "home_hero",
  "status": "draft",
  "starts_at": "…",
  "ends_at": "…"
}
```

**Manque** : champ image (URL ou upload) + aperçu + dimensions recommandées.

### Demandes backend

1. **Corriger** la table / ORM `app_banners` (colonne `code` — schéma désynchronisé).
2. **Documenter** le schéma `POST /v1/admin/marketing/banners` :
   - champs obligatoires ;
   - **nom exact du champ image** (`image_url` ? `imageUrl` ? autre) ;
   - `placement` valides pour l’app client (`client_home`, etc.).
3. **Exposer un upload** si l’image est un fichier (ex. `POST /v1/admin/marketing/banners/upload` ou stockage Supabase/S3 avec URL retournée).
4. **Enrichir** `GET /v1/admin/marketing/banners` et `GET /v1/app-banners` avec `image_url` (ou équivalent) pour affichage liste + mobile.

### Ce que le front livrera dès réception API

| UI | Prérequis API |
|----|----------------|
| Champ image (upload ou URL) + aperçu | Upload ou `image_url` dans POST |
| Emplacement « App client mobile » | Valeur `placement` documentée |
| Miniature dans liste bannières | `image_url` dans GET liste |
| Création fonctionnelle | POST sans erreur `app_banners.code` |

Fichiers concernés :

- `src/features/marketing/pages/MarketingBannerNewPage.tsx`
- `src/features/marketing/api/marketing.service.ts` (`createBanner`)
- `src/features/marketing/api/adminMarketing.mapper.ts`
