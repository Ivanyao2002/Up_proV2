## FR-CREATE-01 — Création d’une franchise : **ne doit pas** exiger `franchiseId`

### Comportement attendu (métier)

Quand l’admin crée une **nouvelle franchise** depuis le backoffice :

- Il renseigne : nom, ville, email admin, téléphone, mot de passe portail, statut initial
- L’API crée l’**entité franchise** + le **compte portail** associé
- **`franchiseId` ne doit pas être obligatoire** — c’est l’API qui génère le nouvel UUID

### Comportement actuel (incorrect pour la création)

Route disponible : `POST /v1/auth/franchise/register`

| Sans `franchiseId` | Avec `franchiseId` existant |
|--------------------|-----------------------------|
| Erreur `AUTH_FRANCHISE_ID_REQUIRED` | OK — crée seulement un membre sur franchise **déjà existante** |

→ Aujourd’hui la route sert à **rattacher un utilisateur** à une franchise seed, pas à **créer** une nouvelle franchise réseau.

### Routes manquantes

| Route | Swagger |
|-------|---------|
| `POST /v1/admin/franchises` | Absent |
| `POST /v1/franchises` | Absent |

### Demande explicite au backend

**Option A (recommandée)** — route admin dédiée :

```
POST /v1/admin/franchises
Authorization: Bearer {admin_jwt}
X-Client-Type: back-office

{
  "name": "UPJUNOO Canada",
  "cityId": "uuid-ville",
  "countryCode": "CA",
  "status": "pending",
  "contactEmail": "admin@franchise.ca",
  "contactPhone": "+1…",
  "adminPassword": "…",
  "adminFirstName": "Admin",
  "adminLastName": "Canada"
}
```

Réponse attendue : `{ franchiseId, memberId, portalLoginEmail, … }`

**Option B** — adapter `POST /v1/auth/franchise/register` :

- Si `franchiseName` + `cityId` + compte admin **sans** `franchiseId` → **créer** la franchise + le membre
- Si `franchiseId` fourni → rattacher un membre à une franchise existante (comportement actuel)

**Champs minimum création (sans franchiseId préexistant)**

| Champ | Obligatoire | Note |
|-------|-------------|------|
| `email` | oui | Login portail franchise |
| `password` | oui | min. 8 caractères |
| `phone` | oui | Profil |
| `firstName` / `lastName` | oui | Admin franchise |
| `cityId` | oui | UUID depuis `/v1/catalog/bootstrap` |
| `franchiseName` | oui | Nom de la nouvelle franchise |
| `countryCode` | recommandé | ex. `CI`, `CA` |
| `status` | recommandé | `pending` / `active` |
| `franchiseId` | **non** | Ne doit pas être requis à la création |
| `devBypass` | dev seulement | Sandbox `api.upjunoo-dev.tech` |

### Côté front (état 8 juin 2026)

- Page `/admin/network/franchises/new` branchée sur `POST /v1/auth/franchise/register`
- Contournement temporaire : sélecteur « franchise cible » — **workaround uniquement**, pas le comportement cible
- Dès que le backend livre la création sans `franchiseId`, retirer ce sélecteur obligatoire

## ZN-GEO-01 — Zones : coordonnées de délimitation pour la vraie répartition

### Problème

Les zones réseau sont affichées sur la carte admin (`/admin/network/zones`, carte live), mais l’API ne fournit pas les **contours géographiques** nécessaires pour dessiner les vraies surfaces de répartition.

### Constat live (8 juin 2026) — `GET /v1/zones`

| Métrique | Valeur |
|----------|--------|
| Zones totales (échantillon) | 27 |
| Avec `geometry` type `Polygon` | **0** |
| Avec `center_point` seulement | 14 |
| Sans géométrie ni centre | 13 |

Exemple zone `ABOBO` : `geometry: null`, `center_point: null`  
Exemple zone `Bouake Centre` : `center_point` OK, mais **pas de polygone**

### Comportement front actuel

- `ZonesMapboxMap` / `AbidjanZonesMap` utilisent `geometry` → polygone si présent
- Sinon fallback : **marqueur au centre** (`center_point`) ou cercle approximatif
- Impossible d’afficher la **vraie délimitation** quartier / zone sans polygone

### Attendu backend

Sur `GET /v1/zones`, `GET /v1/zones/{id}`, `GET /v1/zones/hot`, `GET /v1/geo/hot-zones` :

```json
{
  "id": "…",
  "label": "Cocody",
  "geometry": {
    "type": "Polygon",
    "coordinates": [
      [
        [-3.98, 5.34],
        [-3.97, 5.35],
        [-3.96, 5.34],
        [-3.98, 5.34]
      ]
    ]
  },
  "center_point": {
    "type": "Point",
    "coordinates": [-3.97, 5.345]
  }
}
```

**Champs requis pour la carte**

| Champ | Type | Usage front |
|-------|------|-------------|
| `geometry` | GeoJSON `Polygon` ou `MultiPolygon` | Remplissage + contour zone sur Mapbox |
| `center_point` | GeoJSON `Point` (optionnel) | Label / zoom si pas de polygone |

**Impact** : heatmap, répartition chauffeurs/commandes par zone, surge par secteur — tout reste approximatif tant que `geometry` est `null`.

## FR-PARTNERS-01 — `driversCount` sur `GET /v1/franchises/{id}/partners`

### Problème

Sur la fiche admin **Réseau → Franchises → détail**, l’onglet **Partenaires** affiche une colonne **Chauffeurs**.  
Le front lit `driversCount` sur chaque item de la liste — ce champ **n’est pas renvoyé** par l’API.

### Constat live (8 juin 2026)

`GET /v1/franchises/1bb2bff7-edcc-496d-a87a-4126c19be278/partners` → **HTTP 200**, 5 partenaires.

Champs présents par item : `id`, `trade_name`, `legal_name`, `status`, `contact_email`, `city_id`, `wallet_id`, etc.

**Absent** : `driversCount`, `drivers_count`, ou tout agrégat chauffeurs.

Exemple partenaire `ECO Yopougon` (`39b37776-dcbb-4786-83d9-86ee9ac854c1`) :
- Liste franchise → pas de compteur
- `GET /v1/partners/{id}/drivers` → **10 chauffeurs** (donnée disponible ailleurs)

### Comportement front actuel

```ts
drivers_count: item.driversCount ?? 0
```

→ Tous les partenaires affichent **0** chauffeur tant que l’API ne renseigne pas le champ.

Fichiers concernés :
- `src/features/network/api/franchiseDetail.service.ts` — appelle cette route
- `src/features/network/api/adminPartners.mapper.ts` — mappe `driversCount`
- `src/features/network/pages/FranchiseDetailPage.tsx` — colonne « Chauffeurs »

### Attendu backend

Sur **`GET /v1/franchises/{franchiseId}/partners`**, chaque élément de `items[]` doit inclure :

```json
{
  "id": "39b37776-dcbb-4786-83d9-86ee9ac854c1",
  "trade_name": "ECO Yopougon",
  "status": "active",
  "driversCount": 10
}
```

| Champ | Type | Règle |
|-------|------|-------|
| `driversCount` | `number` | Nombre de chauffeurs rattachés au partenaire (non archivés / actifs selon règle métier) |

**Cohérence** : aligner le nommage avec `GET /v1/admin/partners` si ce champ y est déjà prévu (cf. PA-03).

### Routes liées (ne pas confondre)

| Route | Rôle |
|-------|------|
| `GET /v1/franchises/{id}/partners` | Liste partenaires franchise — **doit** exposer `driversCount` |
| `GET /v1/partners/{id}/drivers` | Détail chauffeurs d’un partenaire (déjà OK) |
| `GET /v1/franchises/{id}/drivers` | Liste chauffeurs franchise (total agrégé, pas par partenaire) |

### Impact

Sans ce champ, le backoffice admin ne peut pas comparer les partenaires d’une franchise sans N appels `GET /v1/partners/{id}/drivers`.
