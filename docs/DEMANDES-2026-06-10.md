## ARCHIVE — LM-VEHICLE-COLOR-01 — Couleur du véhicule sur la carte live admin (fermé)

### Contexte produit

La **carte live** (`/admin/ops/map`) affiche chaque chauffeur avec une **icône véhicule colorée** (blanc, noir, rouge, bleu, etc.) pour faciliter l’identification visuelle en opérations.

Le front est **prêt** : il résout l’URL d’icône à partir d’un code ou libellé couleur catalogue.

### Mise à jour réaudit — **livré API**

Probe `GET /v1/admin/live-map?includeWithoutLocation=true` : chaque chauffeur peut exposer `vehicleColorCode`, `vehicleColor`, `vehicleColorHex`, `vehicleColorId` et un objet `vehicle`.  
Le Swagger live (**v0.4.0**) ne documente pas encore ces champs (0 occurrence de `vehicleColorCode` dans le spec).

**Problème initial (10 juin)** : la route live-map ne renvoyait **aucune information de couleur** — **corrigé côté réponse JSON**.

### Route concernée

```http
GET /v1/admin/live-map?includeWithoutLocation=true
Authorization: Bearer {token_admin}
```

Proxy dev (same-origin) :

```http
GET /upjunoo-api/v1/admin/live-map?includeWithoutLocation=true
```

### Constat API initial (10 juin 2026)

Chaque élément de `drivers[]` exposait notamment :

| Champ présent | Exemple | Suffisant pour l’icône ? |
|---------------|---------|--------------------------|
| `id`, `driverCode`, `profile.displayName` | OK | — |
| `availabilityStatus`, `approvalStatus` | `online` / `approved` | — |
| `rideCategoryCode` | `CONFORT+`, `ECO` | **Non** — catégorie de course, pas couleur carrosserie |
| `vehicleLabel` | `Toyota Corolla · AB-123-CD` ou `ECO` | **Non** — modèle / plaque, pas couleur |
| `location` | `{ lat, lng, heading, speedKmh }` | — |
| `franchiseName`, `partnerName`, `zoneName` | OK | — |

**Absents sur tous les chauffeurs testés** :

- `vehicleColor`, `vehicleColorCode`
- `vehicle_color`, `vehicle_color_code`
- Objet `vehicle` avec `color`, `colorCode`, `colorId`
- `vehicleColorId` / `vehicle_color_id`

→ Le front utilise l’icône **par défaut** (`gps-navigation.png`) pour **tous** les marqueurs.

### Source de données attendue

La couleur existe déjà côté flotte :

- Table véhicule : `color_id` (UUID catalogue)
- Catalogue : `GET /v1/catalog/vehicle-colors` → `{ id, code, label, hex }`  
  Exemples de codes : `WHITE`, `BLACK`, `RED`, `BLUE`, `GRAY`, `SILVER`, …

Sur le détail véhicule (`GET /v1/partners/{partnerId}/vehicles/{vehicleId}`), `color_id` est parfois renseigné — la live-map doit **joindre le véhicule courant du chauffeur** (`current_vehicle_id` ou équivalent) et exposer la couleur **dans la même réponse**, sans N+1 côté front.

**Option recommandée** — objet `vehicle` embarqué (aligné FLT-VEHICLE-DETAIL-01) :

```json
      "label": "Rouge",
      "hex": "#CC0000"
    }
  },
  "location": { "lat": 5.359, "lng": -3.987 }
}
```

**Option minimale** (rétrocompatible, suffisante pour le front) — champs plats sur le chauffeur :

```json
{
  "id": "d41afe75-96bf-4211-a200-35a82bf899b2",
  "vehicleLabel": "Toyota Corolla · 1234AB01",
  "vehicleColorCode": "RED",
  "vehicleColor": "Rouge",
  "location": { "lat": 5.359, "lng": -3.987 }

```

**Option intermédiaire** — uniquement `vehicleColorId` (le front résout via catalogue, mais **1 requête catalogue en plus** — moins performant) :

```json

  "vehicleColorId": "0f7fbeef-d532-468e-9dbc-0fc8d9ec27be"
}
```

### Champs lus par le front (ordre de priorité)

Le mapper `extractLiveMapDriverVehicleColor` accepte **déjà** ces variantes (camelCase ou snake_case) :

| Priorité | Champ |
|----------|--------|
| 1 | `vehicleColorCode` / `vehicle_color_code` |
| 2 | `vehicleColor` / `vehicle_color` |
| 3 | `vehicle.colorCode` / `vehicle.color_code` |
| 4 | `vehicle.color` / `vehicle.colorLabel` / `vehicle.color_label` |
| 5 | `vehicle.colorId` / `vehicle_color_id` → résolution via `GET /v1/catalog/vehicle-colors` |

**Préférence** : renvoyer au minimum **`vehicleColorCode`** (code catalogue stable, ex. `RED`, `WHITE`) **ou** l’objet `vehicle.color` complet.

### Mapping code catalogue → icône front

Le front mappe les codes / libellés vers les PNG dans `public/assets/icon/` :

| Code / libellé catalogue | Fichier icône |
|--------------------------|---------------|
| `WHITE` / `Blanc` | `blanc.png` |
| `BLACK` / `Noir` | `noir.png` |
| `GRAY`, `GREY` / `Gris` | `gris.png` |
| `SILVER` / `Argent` | `argent.png` |
| `RED` / `Rouge` | `rouge.png` |
| `BLUE` / `Bleu` | `bleu.png` |
| `GREEN` / `Vert` | `vert.png` |
| `YELLOW` / `Jaune` | `jaune.png` |
| `ORANGE` / `Orange` | `orange.png` |
| `BROWN` / `Marron` | `marron.png` |
| Absent / inconnu | `gps-navigation.png` (fallback actuel) |

→ Les codes catalogue doivent rester **alignés** avec `GET /v1/catalog/vehicle-colors`.

### Règles métier

| Cas | Comportement attendu |
|-----|----------------------|
| Chauffeur **avec** véhicule assigné et `color_id` renseigné | Renvoyer `vehicleColorCode` + `vehicle.color` |
| Chauffeur **sans** véhicule (`current_vehicle_id` null) | Omettre les champs couleur (front = icône par défaut) |
| Véhicule sans couleur en base | Omettre ou `vehicleColorCode: null` |
| `includeWithoutLocation=true` | La couleur doit être présente **même si** `location` est absente |
| Filtres `franchiseId` / `partnerId` / `cityId` | Ne pas impacter la présence des champs couleur |

### Impact performance

**À éviter** : forcer le front à appeler `GET /v1/drivers/{id}` ou `GET /v1/partners/{id}/vehicles/{vehicleId}` pour **chaque** pin de la carte (rafraîchissement toutes les 30 s × dizaines de chauffeurs).

**Attendu** : enrichissement **serveur** dans la requête live-map existante (jointure véhicule courant + catalogue couleur).

### Contournement front actuel (non optimal)

En attendant l’API :

1. `liveMap.service.ts` charge `GET /v1/catalog/vehicle-colors` en parallèle de la live-map
2. Si seul `vehicleColorId` / `vehicle.colorId` est un jour exposé, le front résoudra le code via ce catalogue
3. Tant qu’**aucun** champ couleur n’est renvoyé → **100 % des marqueurs** utilisent `gps-navigation.png`

### Ce que le front livrera dès réception API

| Feature UI | Donnée backend requise |
|------------|-------------------------|
| Icône véhicule colorée sur la carte | `vehicleColorCode` ou `vehicle.color.code` |
| Mise à jour icône au refresh 30 s | Même champs sur chaque delta WebSocket / polling |
| Popup chauffeur (optionnel) | `vehicle.color.label` pour afficher « Rouge » |
| Panneau latéral chauffeurs (optionnel) | `vehicle.color.label` à côté de `vehicleLabel` |

Fichiers front déjà branchés :

- `src/features/ops/api/liveMapVehicleColor.ts` — extraction couleur
- `src/features/ops/api/liveMap.mapper.ts` — `vehicle_color` + `vehicle_icon_url`
- `src/shared/lib/vehicleMapIcons.ts` — résolution PNG
- `src/shared/components/map/mapboxMarkerElement.ts` — rendu marqueur

### Mise à jour Swagger

Documenter sur le schéma `LiveMapDriver` (ou équivalent § Admin live-map) :

- `vehicleColorCode` (string, nullable)
- `vehicleColor` (string, nullable) — libellé FR
- `vehicle` (object, nullable) avec sous-objet `color: { id, code, label, hex? }`

### Ticket backend synthétique (copier-coller)

> **Titre** : Exposer la couleur du véhicule sur `GET /v1/admin/live-map` (chaque chauffeur)  
>  
> **Contexte** : Le back-office affiche des icônes véhicule colorées sur la carte live. L’API renvoie `vehicleLabel` et `rideCategoryCode` mais **aucune couleur**. Tous les chauffeurs ont l’icône générique. La couleur existe en base (`vehicles.color_id` + catalogue `vehicle-colors`).  
>  
> **Acceptance criteria** :
> 1. Chaque item de `drivers[]` inclut `vehicleColorCode` (code catalogue, ex. `RED`) **ou** `vehicle.color { id, code, label }`
> 2. Jointure sur le véhicule courant du chauffeur (`current_vehicle_id`)
> 3. Si pas de véhicule ou pas de couleur → champs absents / `null` (pas d’erreur)
> 4. Fonctionne avec `includeWithoutLocation=true`
> 5. Swagger mis à jour
> 6. Pas de régression sur `vehicleLabel`, `location`, filtres franchise/partner

### Exemple attendu vs reçu

```json
// Attendu
{
  "id": "…",
  "name": "Cocody",
  "type": "surge",
  "geometry": {
    "type": "Polygon",
    "coordinates": [[[ -3.98, 5.35 ], [ -3.97, 5.36 ], …]]
  }
}

// Reçu (dev)
{
  "id": "…",
  "name": "Cocody",
  "geometry": null,
  "polygon_geojson": null
}
```

**Ce que tu vois** : liste de zones en texte sur `/admin/network/zones` — **pas de délimitation** dessinée sur la carte.

### Demande backend

1. Renseigner `geometry` (GeoJSON Polygon) ou `polygon_geojson` sur `GET /v1/admin/zones` et détail zone.
2. Documenter le format (WGS84, ordre coordonnées `[lng, lat]`).
3. Optionnel : endpoint dédié `GET /v1/admin/zones/{id}/geometry` si payload liste trop lourd.

### Ticket backend synthétique

> **Titre** : Exposer polygones GeoJSON sur zones tarifaires admin  
> **Acceptance** : `geometry` ou `polygon_geojson` non null pour zones cartographiables · Swagger · cohérence avec carte franchise

Fichiers front : `FranchiseTerritoryMap.tsx`, `ZonesMap.tsx`, `adminZones.mapper.ts`.
